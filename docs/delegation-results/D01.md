# [ORQUEST][AGENTE A][D01][ESTADO: ENTREGADO]

## Objetivo y resultado

Se entregó un contrato aditivo de continuidad por tarea para revisión. La base
P1a de sesión, intentos, mensajes y snapshots se reutiliza; no se modificaron
SQLite, daemon, MCP, adaptadores ni UI.

## Inventario y decisiones

- Existían `taskSessionId`, `attemptIndex`, mensajes paginados, snapshots y
  metadatos solicitados/efectivos. Los jobs y mensajes ya preservan identidad de
  sesión/workspace; los mensajes impiden cambiar su `jobId` por actualización.
- Se añadieron identidad de proveedor por mensaje, destinatario, intención,
  objetivo de despacho y relación separada `TaskMessageAttemptDispatch` para
  que una cola pendiente se enlace a un futuro intento sin cambiar `jobId`.
- El contexto del orquestador es por turno y separa solicitado/efectivo. Inputs
  externos no permiten declarar `runtime`; registros históricos permanecen
  legibles con sus contratos compactos originales.
- Se añadió retry por tarea con selector de origen opcional, clave obligatoria y
  contexto declarable. Continuar/reintentar nunca inyectan en un intento activo;
  una tarea activa responde `TASK_ACTIVE` hasta que D08 implemente la cola.
- Los cursores de intentos y mensajes quedan ligados a `taskSessionId`, dirección
  y frontera de orden. El despacho futuro verifica pertenencia transaccional y
  admite una única relación mensaje→intento.
- La idempotencia nueva reserva tarea + clave para todas las operaciones de
  continuidad; la operación y payload pertenecen al fingerprint. Solo hay replay
  para la misma operación/contenido; cualquier reutilización distinta devuelve
  `IDEMPOTENCY_CONFLICT`. El alcance histórico de jobs (workspace + clave) queda
  sin cambios.

La especificación con endpoints HTTP y herramientas MCP propuestas está en
[continuity-contract.md](../continuity-contract.md). Es un contrato para D04/D05,
no una implementación de esas superficies.
